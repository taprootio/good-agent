# GA0008 — Make `good-agent check` honour .gitignore

## Scope

Defect found adopting 0.1.0 in taproot. That repository keeps per-session
worktrees under `.claude/worktrees/`. The directory is gitignored and every
worktree has its own `.git` file, but the guard's directory walk
(`discover` in `src/discover.mjs`) does not read `.gitignore`, so it scanned
every `AGENTS.md` and `CLAUDE.md` copy inside them, reported duplicates and
failed. The workaround was `"ignore": [".claude/worktrees/**"]` in
`good-agent.config.json`. The guard should not need it.

- When the scan root is inside a git work tree, `discover` takes its
  candidates from `git ls-files --cached --others --exclude-standard -z`
  (run with `-C <root>`, output split on NUL). Tracked files and untracked
  files that no ignore rule covers are checked; ignored files are not. A
  file that is tracked and also matches an ignore rule stays checked, which
  is how git itself treats it.
- Git lists a nested repository (a submodule, or an untracked directory with
  its own `.git`) as one directory entry at most. Discovery does not enter
  it. A nested repository is another repository: run `good-agent check` in
  it. This is stated in design 4.1.
- The directory walk stays as the fallback when `git` cannot be run, the
  root is not inside a work tree, or the root is itself an ignored directory
  (git lists nothing under an ignored directory, and an empty list would
  hide every file). The result is the same as 0.1.0 in those cases.
- The existing skips apply on top in both modes: the ignored directory names
  (`node_modules`, `.git`, `coverage`, `dist`, `build`, `public`, `.next`,
  `out`) and the config `ignore` globs.
- Paths given on the command line (`good-agent check <paths>`) stay checked
  as given: an instruction file among them is added to the checked set even
  when git ignores it. The config `ignore` globs and the ignored directory
  names still apply to it, as they do to any other file. A path outside the
  root is not added.
- `docs/design.md` (4.1 and the noise controls in 3, 4.2 for `check` with
  paths), the CLI help text, the README and the CHANGELOG record the
  behaviour in the same change.

Not in scope: reading `.gitignore` in the fallback walk (a hand-written
gitignore matcher is exactly the surface that drifts from git), `.ignore`
or other tools' ignore files, and changing how `review` finds files.

## Acceptance

- A fixture repo with a gitignored per-session worktree holding copies of
  `AGENTS.md` and `CLAUDE.md` checks clean (exit 0, only the root files
  listed) once it is a git work tree, and the same files copied outside any
  work tree take the fallback walk and report the duplicates, so both
  paths are covered.
- Tests cover: untracked and unignored included; ignored excluded; tracked
  but ignored included; config `ignore` and ignored directory names applied
  on top in git mode; a root that is a subdirectory of a work tree lists
  only files under it; a root that is itself ignored falls back to the
  walk; a nested repository is not entered; git missing from `PATH` falls
  back; an explicit path to an ignored instruction file is checked, and one
  outside the root is not added.
- `node --test`, `npm run typecheck`, `npx @taprootio/trellis check` and
  `node scripts/good-agent.mjs check` are green. The repository's own
  `good-agent.config.json` is unchanged; its `ignore` list stays because
  the fixtures are tracked files and so still need it.

## Notes

- Found 2026-11-02 by the GA0006 adoption in taproot; reported by the owner.
- Decision under work-task step 3: git is the source of truth in a work
  tree, with no attempt to mimic `.gitignore` semantics in the fallback.
  Recommended over a hand-written matcher because git already answers the
  question exactly, including nested `.gitignore` files, `.git/info/exclude`
  and the global excludes file.
- Decision: nested repositories are not entered in git mode. Entering an
  untracked, unignored worktree would reproduce the reported defect.
- Decision: no new flag. `--no-gitignore` would add a surface for a case
  nobody has hit; explicit paths already cover checking one ignored file.

## Risks

- Git is slower than nothing on a huge work tree. `ls-files` is
  index-backed and faster than the walk it replaces; the reviews runner
  already calls it on every round.
- A user with `safe.directory` trouble gets the fallback walk silently, the
  0.1.0 behaviour, rather than a failure.
- A repository that tracks a worktree-like directory is still checked, by
  design.

## Plan

1. `gitCandidates` and the git mode in `discover`, the `include` option, and
   `analyze`/`runCheck` passing the explicit paths. Narrow check: the
   existing discover, CLI and rules tests stay green (the rules test runs
   every fixture inside the outer work tree, so it exercises git mode on
   the existing fixtures). Commit.
2. Fixture `test/fixtures/gitignore/worktrees/` and `test/discover.test.mjs`
   cases from the acceptance list. A fixture inside this repository is
   always inside the outer work tree, so each test copies it to a temporary
   directory: `git init` for the git case, no `git init` for the walk case.
   The copies under the fixture's `.claude/worktrees/` are covered by the
   fixture's own `.gitignore`, so they are added to this repository with
   `git add -f`. The fixture has no `expected.json` (the rules test would
   run it inside the outer work tree, where those copies are tracked), and
   the repository's `test/fixtures/**` config ignore keeps
   `node scripts/good-agent.mjs check` green. Narrow check: `node --test
   test/discover.test.mjs test/cli.test.mjs`. Commit.
3. Docs: design, CLI help, README, CHANGELOG. Narrow check: `node
   scripts/good-agent.mjs check` and the docs snippet test. Commit.
4. The diff review loop against the start commit (internal, then
   external), running the narrow checks after each fix. Then the gates once
   on the final candidate (`npx @taprootio/trellis check`, `node --test`,
   `npm run typecheck`, `node scripts/good-agent.mjs check`), rerun if a

   check` (the one gate rerun after the close-out), commit.
