# GA0003 — Write the write-task and work-task playbooks with the review loop

## Scope

Per [docs/design.md](../../docs/design.md) section 12, "What good-agent
ships", items 1 to 3. Source material: the Taproot sibling checkout at
`../taproot` (private; commit `23496ea60`, 2026-10-30): `docs/playbooks/work-task.md`
and `scripts/review-exchange/README.md`; and Trellis's `trellis/playbooks/`
(`../trellis`, also scaffolded into this repo).

- `skill/write-task/SKILL.md`: review the problem against the codebase and
  the backlog; write the story (one-line summary, Scope with checkable
  acceptance criteria, Notes with decisions and rejected alternatives, Risks,
  dependencies, effort); review it internally with the story prompt until
  clean; review it externally with the other AI tool until clean; finalize
  into the backlog (regenerate when Trellis is present).
- `skill/work-task/SKILL.md`: ground in the repo's canonical file; read and
  verify the task; propose refinements; branch, with no file edit before
  this step so Trellis's clean-tree rule holds (Taproot's own loop edits
  the task before branching; this loop does not); write the refinements and
  a plan with commit checkpoints into the
  task file on the branch; review the plan internally, then externally;
  choose the least-cost runtime that meets the quality floor for each slice
  (generalize Taproot's "select a runtime deliberately" and "review cost
  ceiling" without naming models); implement; review the work internally
  until clean, then externally until clean; close out; hand off without
  pushing.
- `skill/review-loop/SKILL.md`, a skill of its own that the other two invoke
  by name and that also triggers on "review this": fresh context, read-only,
  factual prompt built from the task and the diff and never from the
  author's summary, severity semantics (`blocker`, `warning`, `nit`),
  confirm every finding against the cited code before fixing, fix, repeat
  with the whole current diff and the prior findings until `[]`, caps (five
  internal passes then a focused confirmation; external rounds capped at ten
  when Codex reviews and five when Claude reviews, counted per prompt type
  so story, plan, diff and design rounds have separate caps, counting only
  completed rounds; a failed or unsafe round keeps its number but does not
  count, per design 12 and GA0004), design review on
  non-convergence, and what goes into the durable record: independence,
  round count, findings and dispositions, never a model or vendor name. It
  runs the external round with `good-agent review` (GA0004). Until GA0004
  lands it carries an interim passage (run the other tool's CLI by hand
  with the same prompt file); GA0004 rewrites that passage so only a
  no-good-agent-installed fallback remains.
- The prompts the loop uses, as files the runner (GA0004), a tool's own
  subagent and a human all read, inside the skill so `init --skill`
  installs them: `skill/review-loop/references/review-diff.md`,
  `review-story.md`, `review-plan.md`, `review-design.md`, linked from
  `SKILL.md` one level deep as the Agent Skills spec recommends, each with the
  "close the room for hedging" rules from section 8 of
  `../taproot/docs/playbooks/work-task.md` and the two endings described
  below. Every reviewer prohibition (no edits, no state-changing
  commands, no questions in place of findings, no scope expansion) lives in
  these prompt files; the skill states the loop, the prompts state the
  reviewer's rules. Each prompt file is a body plus two endings in marked
  sections: the manual ending (used by a reviewer run by hand or by a
  tool's own fresh subagent) requires a fenced JSON array as the final
  block even when empty; the runner ending (used by `good-agent review`)
  requires the schema object `{"findings":[...]}` that structured output
  enforces. The caller appends exactly one.
- Seam points: the playbooks name Trellis's `regenerate`, `check`,
  `branch-naming`, `gates` and `attribution` when the repo's AGENTS.md has a
  Loop contract. The review policy (who reviews whose work, model and
  effort ceiling) lives in the `review` block of `good-agent.config.json`
  (design 4.6) and is stated in prose for AI tools in a separate
  `<!-- BEGIN GOOD-AGENT -->` block in AGENTS.md, never inside the Trellis
  block. Without Trellis the playbooks still work; backlog steps become
  "record it where this repo keeps tasks".
- This repo adopts them: its `good-agent.config.json` gets the `review`
  block, its AGENTS.md gets the good-agent block (hand-written from the
  template in the `review-loop` skill), and the "Working here" bullet in
  AGENTS.md that currently points at `trellis/playbooks/work-task.md` plus
  an external round is repointed at `skill/work-task/SKILL.md` and
  `skill/review-loop/SKILL.md` by source path (checked by `links/broken`),
  so the repoint itself needs no installed copy. Trellis's own
  playbooks are not edited (open question 1).
- The `work-task` skill writes the plan into a `## Plan` section of the
  task file, on the task branch, before requesting plan review, so the plan
  prompt has one input (`--task`) and the review history stays under the
  task's id.
- docs/design.md section 9's layout already lists the four skills and the
  `references/` prompts; keep it in sync in the same PR.

## Acceptance

- Each skill is under 250 lines and passes GA0001's `test/skill.test.mjs`.
- A dry read-through by a fresh context, given only the playbook and a
  sample task, produces the loop's steps in order with no step that depends
  on Taproot-specific tooling (`verify-changed.sh`, `TRxxxxx`, Tilt).
- `skill/review-loop/SKILL.md` states the loop (fresh context, confirm
  before fixing, repeat until `[]`, caps, design review, durable record),
  and each `references/review-*.md` states every reviewer prohibition and
  carries both endings, the manual one requiring the fenced JSON array as
  the final block even when empty.
- In a consumer fixture that has only the installed copies (no `skill/`
  tree from this repository), every prompt a skill names resolves.

## Notes

- Taproot's playbook carries Taproot policy (signed verification, computer
  use, creator surfaces, Postgres categories) that stays in Taproot. Only the
  loop moves.
- The split with Trellis (design 12, "Overlap with Trellis"): Trellis owns the
  backlog lifecycle, good-agent owns the loop. Changing Trellis's own
  playbooks, here or in the Trellis repo, is a separate decision and not in
  this task.

## Risks

- Generalizing the runtime-selection language without model names can make
  it vague. Keep the rule shape ("balanced, current generation, high effort
  for review; premium only on request") and put the concrete values in the
  `review` block of `good-agent.config.json`.

## Refinements (2026-11-01)

- Owner decision (2026-11-01): once good-agent is ready, Trellis's own
  `work-task` playbook is removed in favour of good-agent's skills. That
  change lands in the Trellis repository and is tracked as GA0007; this
  story still edits nothing under `trellis/playbooks/`.
- The two review endings are marked in each prompt file with
  `<!-- ENDING: manual -->` and `<!-- ENDING: runner -->` sections so a
  caller (or the runner) can select one by marker.

   `<!-- BEGIN GOOD-AGENT -->` block template (review policy prose that

   the branch.

   the `<!-- BEGIN GOOD-AGENT -->` block in AGENTS.md from the template in
   the review-loop skill, the "Working here" bullet repointed by source

   depends on it.

   review loop; close out (`completed/tasks/`, `status: completed`,
   `completed_on`, start sha and rounds recorded).
