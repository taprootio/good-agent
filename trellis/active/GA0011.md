# GA0011 — An open-pr skill that checks whether a version bump is required

## Scope

Found 2026-11-02. PR #5 (GA0008, GA0009) merged into `main` at version
0.1.0. The owner expected the merge to release. In this repository the
version bump in `package.json` on `main` is the release
(`.github/workflows/release.yml`, `docs/design.md` section 8), and nobody
bumped it. Nothing in the PR flow or the review asked the question.

- `skill/open-pr/SKILL.md`, a fifth shipped skill, followed by an AI tool to
  open a pull request for the current branch, in this order:
  1. Confirm the branch is on top of the base branch and the gates the
     repository names (the `gates` seam point, or its canonical file) have
     run on the final tree.
  2. Decide whether the PR needs a version bump: find the package manifest
     (`package.json` here; what to do when a repository has none or has
     several), compare its version on the branch with the base, and look at
     what the diff touches (the files the package publishes, and entries
     added under the changelog's Unreleased heading). When shipped behaviour
     changed and the version did not move, stop and ask the owner whether the
     PR is the release; if so apply the repository's bump rules (good-agent:
     `docs/design.md` section 8), make the bump, move the Unreleased entries
     under the new version heading with the date and update any status line
     that names the version; if the PR is deliberately not a release, say so
     in the PR body. A repository with no release flow skips the step and
     says so.
  3. Check the commits carry no attribution the repository forbids and the
     branch follows the repository's naming.
  4. Write the PR body from the repository's conventions (what changed,
     gates, review rounds and dispositions, what the merge does, for a
     release what the release workflow will do) and open the PR only when the
     owner has approved the push.
- `skill/review-loop/references/review-diff.md` gets a check, in the shape of
  its other checks, that a diff which changes shipped behaviour or adds
  changelog entries either carries the version bump its repository's release
  flow needs or says why it is not a release, reported as a finding when
  neither is true.
- Wiring: `good-agent init --skill` installs it like the other four (the
  install scans `skill/`, so no code changes); `docs/design.md` sections 5.3,
  9, 10 and 12 name it; `README.md` lists it; `CHANGELOG.md` has an entry under
  `## Unreleased`.

## Acceptance

- `node scripts/good-agent.mjs init --skill --cwd <tmp>` installs `open-pr`
  into `.agents/skills/` and `.claude/skills/` with the generated marker; the
  consumer test lists five skills and every relative link in the new skill
  resolves.
- The installed copy passes the skill validator; `npm pack --dry-run` lists
  `skill/open-pr/SKILL.md`.
- A test fails if `review-diff.md` loses the version-bump check, and one
  fails if `open-pr` stops naming the release decision steps.
- `npx @taprootio/trellis check`, `node --test`, `npm run typecheck` and
  `node scripts/good-agent.mjs check` are green.

## Notes

- Versions are not touched here. The 0.2.0 bump is GA0010 on its own branch;
  this entry sits under `## Unreleased` and merges trivially after it.
- Decision: the skill reads the repository's rules for bumps from its
  canonical file and the design documents it names, as the other skills read
  their seam points; the good-agent rules are an example, not a requirement.
- Decision: the skill asks the owner when shipped behaviour changed and the
  version did not move, and never bumps on its own: whether a merge is a
  release is the owner's call.
- Decision: no new code. `installSkills` scans `skill/` for directories with
  a `SKILL.md`, so the tests carry the change.

- Deviation, recorded for the closeout: steps 1 to 3 were written before the
  plan gate ran. The plan was then reviewed, and the review's findings were
  folded in; the gate was run afterwards over the finished plan and diff.

## Risks

- A reviewer prompt that over-flags: a repository with no release flow, or a
  docs-only diff, must not produce findings. The check names both exclusions.
- `open-pr` and `work-task` step 11 could each defer to the other for the
  push. Settled: `open-pr` owns the push and open commands and runs them
  only on the owner's go-ahead for that pull request; step 11 tells the AI
  tool to run `open-pr` and otherwise forbids pushing.
